## Strongest supported contribution

Frame the paper around **when successful checks do not validate the edited source**.
The natural motivating observation is the unchanged native Requests environment:
zero of four clean/reference pairs qualified, and declared offline setup interventions
restored all four without changing assertions. Existing controls span four Python
repositories, and the original factorial mechanism replicates on Windows and Linux.
This is a specific empirical failure and reproducible resource, rather than a claim
to invent import resolution, editable installation, local inference or agent UI.

The new process-boundary experiment strengthens this argument. A successful fresh
preflight selected the intended checkout, but a later process could select a foreign
copy with the same version. Across16 fixed conditions in each of two fresh Windows
repetitions, exit-only, version-plus-exit and preflight-plus-exit each made4 wrong
checkout verdicts and8 unsupported source claims. A receipt from the actual check
retained8 decisions with zero wrong/unsupported claims and abstained on8 foreign
origins. The always-unknown baseline retained zero decisions. This reports coverage
alongside error, preventing an all-abstention policy from looking useful simply
because it makes no false claims. Conditions cover two layouts of one synthetic
package; repetitions are not independent repositories, and these are not model repairs.

Do not present the inspect-only source guard as binding every later Python command.
Its fresh probe records one process. A same-process diagnostic receipt is demonstrated
only in the new controlled assertion; production test instrumentation, multiple
modules, plugins, compiled extensions, file changes during import and worker processes
still require evaluation. No test or official verifier was edited for this experiment.
