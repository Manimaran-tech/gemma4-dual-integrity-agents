# Research contribution and remaining evidence gaps

Working contribution: an executable diagnostic resource showing when coding-agent
feedback validates a different source from the checkout being edited, and a workflow
that distinguishes generated changes, completed commands, source observations and
independently verified repairs.

The strongest natural observation is the four exposed Requests fixtures: unchanged
native setup qualifies none of the clean/reference pairs; declared offline source
installation restores all four under unchanged assertions. The process control then
isolates a different boundary: a successful preflight does not bind a later test
process, even when versions and assertions match. Its source-qualified policy must
report coverage as well as unsupported claims, because abstaining on everything
would avoid false claims without helping a developer.

The two phone episodes add an operational counterexample: successful tool execution
and a completed generation loop can still produce no production edit. They are
negative observations on one reused issue, not an accuracy comparison or proof of a
better mobile agent. They should support the evidence-state distinction, not carry
the main novelty claim.

Closest overlap includes SWE-agent's interface design, HarnessFix's harness diagnosis,
HarnessTester's contract testing, STING's regression-test adequacy, existing Python
import guidance, and Google AI Edge Gallery/AutoDroid-V2's mobile workflows. Our
proposed distinction is the specific empirical source/process failure and a runnable
resource with supported-decision coverage and missing-result accounting. We do not
claim invention of import resolution, offline inference, agent UI or harnesses.

The resource/empirical-paper route currently has stronger support than an application
award argument. An application claim still needs a useful evaluated workflow. A
main leaderboard win is not a prerequisite, but the paper must show why its insight
changes a software-engineering decision rather than only documenting our setup.

Before final filing:

1. Replicate the new process control on Linux and extend it to several real projects
   and relevant process boundaries. Separate constructed mechanisms from natural
   prevalence; no blanket provenance guarantee for plugins/workers/extensions.
2. Measure supported feedback decisions and practical workflow utility with a frozen
   matched comparison. Preserve negative and unknown results.
3. Complete one sanitized artifact with fresh reproduction, exact claim/version
   mapping, explicit licenses and public-access checks. The server v12 resource does
   not cover the newest local evidence.
4. Finish one consistent writeup within the actual platform word count. The reviewed
   local draft corrects stale phone/publication status; final entry and DOI remain
   pending.
