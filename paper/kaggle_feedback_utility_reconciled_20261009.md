# When passing tests validate the wrong source

*Reproducible feedback controls for offline coding agents*

Local reconciled evidence draft, October9,2026. The saved Kaggle writeup and
server resource12 are unchanged. Two actual on-device episodes have completed
independent grading and failed without production edits; the original study and
separate adaptive pilot remain distinct. This is not a final Paper Track entry.

## Abstract

Offline coding agents need feedback about the source they edited. A passing check
can instead exercise an installed copy, and a successful source preflight need not
describe a later test process. We study these failures with source-bound native
diagnoses and unchanged assertions. Four Requests cases yield zero qualifying
clean/reference pairs under unchanged native setup; declared offline installation
restores all four. Synthetic native loops expose source edits across ten public
cases from four Python repositories. Independent controls reproduce false acceptance
and false rejection with identical package versions. A new sixteen-condition process
experiment, repeated twice per OS on Windows/Linux, shows that successful preflight-based feedback still
makes four wrong checkout verdicts per repetition. Check-process origin receipts
retain eight correct decisions and abstain on eight foreign origins. A separately frozen three-library API study retains144 supported decisions with
zero wrong verdicts in each of288 constructed Windows and288 Linux conditions. Ten Gemma
development studies preserve missing outcomes without establishing repair gains.
We prepare an executable diagnostic resource and define separate evidence states
for generation, execution, source identity and independently verified repair.

## Introduction

A local model can generate a plausible edit while receiving irrelevant feedback.
If Python imports an installed package instead of the edited checkout, tests can
reward an unfixed repository or reject a correct change. Matching versions cannot
distinguish the copies. Likewise, a completed search can read inherited standard
input rather than source files. The problem is whether an observation belongs to
the intended task, source and process before its verdict is interpreted.

Our contribution is a reproducible empirical resource for this feedback boundary.
It combines a natural native-harness diagnosis, controlled setup interventions,
fresh mechanism experiments and a model-outcome audit that preserves missingness.
We do not claim a new import mechanism, model architecture or first offline agent
interface. The important property is that a verdict, a valid origin probe and a
verified issue repair are different observations.

We ask three questions: Does native validation exercise the intended checkout?
Which evidence reduces wrong source claims while retaining useful decisions?
Does verified integration establish improved Gemma repair performance? The final
question separates a reliable measurement process from a capable repair model.

## Feedback contract and methods

The workflow records four states: a generated edit, a completed command, the input
and source actually exercised, and an independently verified repair. Advancing one
state does not automatically establish the next. Unknown results remain unknown.
In particular, a cancelled run can contain a real edit, while a successful generation
loop can contain no correct production change.

Plans freeze case IDs, problem-only inputs, source/package hashes, dependencies,
assignment order and notebook cells before execution. Native integration verifies
all100 organizer Python sources. Executed source, archive bytes, transports and
full output are reconciled. Hashes establish byte identity; a recorded scalar replay
does not authenticate a grader or rerun inference. Reference fixes and protected
validation remain evaluator-only. All competition cases used here are exposed
public development cases, not holdouts.

### Natural source-selection diagnosis

A metadata-ranked panel assigns four cases each from Requests, FastAPI and Rich.
The four Requests cases fail fixture qualification: a clean base must fail and its
official reference must pass under the same verifier. No failed case is replaced.
Inventories show host Requests2.32.4 imported in all eight unchanged clean/reference
checks, with identical hashes across conditions. The native backend adds the checkout
root to PYTHONPATH, although these checkouts place Requests under `src/requests`,
and skips editable installation.

Two declared diagnostic interventions install the actual checkout offline using
`--no-index --no-build-isolation --no-deps`: immediately before native pytest, or
before baseline creation and reference/test-patch application. Interpreter inventories
record the source selected by each check. The official verifier and assertions are
unchanged. These setup observers diagnose the evaluation environment; they are
separate from the allowed agent-side helper and do not count as generated repairs.

The helper probes one flat/src module in a fresh isolated interpreter. Correct
origins skip installation; otherwise permitted offline setup must recheck origin
and preserve tracked source. Missing build backends, ambiguous layouts and persistent
shadowing are explicit negative observations. A source-only validation environment
can handle an unavailable backend, but subsequent checks must actually use it.

### Integration and independent controls

A native panel fixes three cases each from Requests, FastAPI and Rich, plus the
sole public HTTPX case. Synthetic predetermined replies exercise original compilation,
tools and budgets without loading a model. Forty loops test inert edit visibility
under inspect-only, conditional installation and explicit-source conditions. Markers
are restored and patches remain empty; this is integration evidence.

Independent drivers create disposable repositories and isolated interpreters without
network access. Fixed assertions, same-length edits and separate bytecode caches
test flat/src layouts, missing backends and foreign-copy shadowing. The original
factorial control crosses checkout state, foreign-copy state and selected origin
in eight conditions, all with version0.0.1 and byte-identical assertions. Its frozen
invariants replicate on Windows and Linux.

The new process-boundary control adds two layouts of one synthetic package. Preflight
always imports the intended source. The subsequent assertion process receives either
the intended or foreign source path; neither file nor assertion changes between
probe and test. Each test records its actual module path/hash and version. Sixteen
conditions run in each of two fresh Windows and two fresh Linux repetitions. Compare exit-only,
version-plus-exit, preflight-origin-plus-exit, test-process-origin-plus-exit and
always-unknown policies on identical observations. Report decision coverage, wrong
checkout verdicts and unsupported source claims; abstention is not a failing repair.

### Multi-library feedback decision utility

A separately frozen study captures production Python source and licenses from
packaging26.3, idna3.20 and urllib3 2.8.0. Fixed API assertions exercise name
normalization, label length and case-insensitive headers. One declared same-length
fault per library constructs faulty/original workspace and foreign copies, keeping
versions equal. These are injected counterfactual faults, not natural issues or
model repairs. The48-condition grid per library crosses flat/src layout, two source
states for each copy, selected origin and three process boundaries: a fresh process
in the same interpreter, a second isolated interpreter, and a nested worker.
Two repetitions per OS assign288 Windows and288 Linux conditions. Observer-off/on checks use identical
assertions; the observer records root/API-module file origins after execution.
No dependencies are installed. Final file hashes are observations, not authentication
of every executed byte or import. The exact frozen source/protocol also completes on Linux.

## Results

All24 native Requests verifier checks complete. Unchanged setup gives three
unverified-reference pairs and one already-passing clean base. Both installation
conditions select workspace source and restore all four discriminating fixtures.

| Setup | Workspace imports / checks | Qualified pairs / cases |
| --- | ---: | ---: |
| Unchanged native setup | 0/8 | 0/4 |
| Install immediately before pytest | 8/8 | 4/4 |
| Install before baseline and patch application | 8/8 | 4/4 |

This is a paired result on four exposed cases; repeating their setup does not
increase the number of independent issues. Qualification establishes a usable
feedback fixture, not model repair success or correctness beyond its assertions.

Inspect-only native loops see edited source in six of ten cases. Conditional
installation reaches nine, with three Requests installs; HTTPX remains negative
because its build backend is missing offline. The explicit source environment
reaches ten of ten. An initial manifest omission stops execution and is preserved;
an execution-only amendment fixes that omission without changing assignments.
The agent did not autonomously discover these interventions in this synthetic panel.

The original eight-cell control exhibits false acceptance of an unfixed checkout
and false rejection of a correct edit when a foreign copy is imported. The new
process control shows that even an independently successful preflight does not
bind a later test. All four Windows/Linux repetitions have identical policy outcomes:

| Policy | Decisions /16 | Wrong checkout verdicts | Unsupported source claims | Unknown /16 |
| --- | ---: | ---: | ---: | ---: |
| Exit only | 16 | 4 | 8 | 0 |
| Matching version + exit | 16 | 4 | 8 | 0 |
| Successful preflight origin + exit | 16 | 4 | 8 | 0 |
| Actual test-process origin + exit | 8 | 0 | 0 | 8 |
| Always unknown | 0 | 0 | 0 | 16 |

Four foreign-copy verdicts per repetition are coincidentally correct, but still
do not validate the intended source. The qualified policy preserves eight useful
decisions, unlike the always-unknown control. These are constructed conditions on
one package in two layouts; they establish a mechanism and evidence boundary, not
natural fault prevalence, broad test adequacy or model accuracy. The exact frozen mechanism now replicates on Linux; this does not establish
cross-project generalization by itself.

### Supported decisions across real-library APIs

All288 conditions and576 observer-off/on API checks per OS complete on Windows/Linux, with
zero unknown executions and zero assertion-exit changes from observation. Each
library qualifies its unchanged original and injected-fault pair. Results are
identical across both OSs, the three libraries and all measured process boundaries. Counts below are per OS:

| Policy | Decisions /288 | Wrong checkout verdicts | Unsupported source claims | Unknown /288 |
| --- | ---: | ---: | ---: | ---: |
| Exit only, matching version, or successful preflight | 288 | 72 | 144 | 0 |
| Actual API-process root/module evidence | 144 | 0 | 0 | 144 |
| Always unknown | 0 | 0 | 0 | 288 |

Thus source-qualified feedback retains144 supported decisions while abstaining
on foreign-copy checks. Each library contributes48 supported decisions and24 wrong
exit-only verdicts. The endpoint is useful feedback classification under controlled
source selection, not full-project regression safety, natural prevalence or repair
accuracy. Observer-off/on median check times are0.125s/0.141s on this Windows host;
Linux medians are0.199s/0.206s; fixed order and cache effects prevent a causal overhead claim. Kaggle global sitecustomize emits a nonfatal missing-wrapt warning in all576 Linux API checks; assertions/source receipts complete, but clean startup is not established. Worker receipts
cover these explicitly invoked workers, not arbitrary distributed execution.

### Other feedback boundaries

Native search controls observe descriptor zero as an empty FIFO. Pathless ripgrep
returns no matches despite an unchanged source literal; explicit paths restore
matches. Empty/matching pipes, null input and absent-literal controls distinguish
input selection from source absence. Twenty-four charged native commands use
synthetic replies and empty patches; six fresh controls reproduce the mechanism.
The established heuristic is documented in [ripgrep's implementation](https://github.com/BurntSushi/ripgrep/blob/master/crates/core/flags/hiargs.rs).
GPU descriptor-zero identity was not captured.

One model-study reproduction has no returned tool result. A private replay shows
constant invalid mocked input stalling until a local timeout, while finite input
completes. Fresh synthetic controls reproduce this mechanism. Missing intervals
remain censored rather than being assigned zero time or a failing assertion.
This diagnoses one reproduction pattern, not every timeout or the library issue.

### Model performance and missing outcomes

Ten terminal Gemma development studies retain120 assigned slots,109 completed
executions and11 unattempted slots. They reuse two exposed six-case panels and
cannot be pooled as independent tasks. Twenty-one repeated repair observations
are independently verified; they are not twenty-one unique solved issues.

The historical nonnegative-exit convention retains40 known verdicts and80 unknown
or unattempted slots. A conservative sensitivity treats five exit2 collection/
interrupt results as unknown, leaving35 known and85 unknown/unattempted slots.
Native grades remain unchanged in the retained records. Worst-case paired outcome
bounds include zero in every study, so general harness superiority is unresolved.
These are loose sensitivity bounds, not confidence intervals or imputed results.

The latest bounded-writer study verifies one production repair in each arm on the
same Rich issue. A shorter duration on that one successful case does not establish
an overall speed or accuracy gain. Earlier protocol and search interventions improve
some observed behaviors without demonstrating reliable repair improvement.
Protected-test conflicts and stopped assignments remain in the audit.

### Native mobile workflow observations

One physical native E2B CPU2 episode on an S24 FE now completes in222.868s,
including shutdown. Six model responses lead to one successful root listing and
four failed repository actions, then `TOOL_FAILURE`; no production source changes.
Directory search against a file-only tool and invented paths are observed failure
mechanisms. The original12-slot protocol preserves0 verified repairs,1 verified
failure and11 unknown results, including three pre-inference failures and eight
unattempted slots. Independent CPU grading fails both clean base and the unchanged
native export while passing the official reference patch. Exact executed source,
input and output transports reconcile. This establishes a genuine negative pilot,
not repair accuracy or interface superiority.

The run retains528 verified memory samples, with Calculator foreground in528/528;
sampled maximum whole-app PSS is2923.55MiB. Battery observations span39.8–40.9°C,
with thermal status0–1 and no safety stop. Foreground presence is not responsiveness,
sampled PSS is not exact peak/model-only memory, and battery temperature is not
energy. API36 budget fields are unavailable. Verified uninstall removes both added
test apps/private data. Cross-device and practical UI-utility claims remain untested.

The frozen phone study plans six genuine public cases with two repeats and separate
clean/patch/reference grading. Its incomplete outcomes and source-reviewed negative
pilot are reported above; the existing server resource12 excludes these new receipts.
The original study is retained before a separate adaptive tool-interface revision.
That revision adds bounded directory-or-file literal search, existing source paths
and hashes, and actionable recovery guidance, following
[SWE-agent's interface-design motivation](https://arxiv.org/abs/2405.15793).
It passes three host boundary tests and ten model-free checks on the physical phone,
including traversal, symlink, stale-hash and protected-write rejection. These are
integration checks, not model repairs.

One separately assigned exposed adaptive episode on the same previously failed
case ends in96.894s. It completes three model responses and two successful tool
observations, but searches `docs_src`, finds no literal `$ref` match, and ends with
an unexecuted promise to search further. It reads no production file and makes no
edit, despite `generation_loop_succeeded=true`. All247 sampled foreground reports
show Calculator; sampled maximum whole-app PSS is3107.25MiB, with battery39.2–39.9°C
and thermal status0. Both added apps/private data are removed and absence verified.
Fresh independent grading fails clean base and the unchanged native patch while
passing the official reference; exact executed source, input and API output reconcile.
This adaptive,
sequential single-case observation is outside the original12-slot study; it cannot
establish a causal effect, repair rate, speed gain or a second independent task.
It provides a concrete counterexample to treating tool or loop completion as
evidence of a completed coding task.

## Related work

[SWE-agent](https://arxiv.org/abs/2405.15793) studies agent–repository interfaces;
[Agentless](https://arxiv.org/abs/2407.01489) separates localization, repair and
validation. [HarnessFix](https://arxiv.org/html/2606.06324v2) diagnoses and repairs
harness flaws from traces. [HarnessTester](https://arxiv.org/html/2610.04921v1)
studies harness test adequacy and contract-aware test generation. Our preparatory
boundary tests are not a coverage or mutation-adequacy measurement.

[STING](https://arxiv.org/html/2604.01518v1) strengthens weak benchmark assertions.
We instead demonstrate wrong source under unchanged assertions. [Harness or Model?](https://arxiv.org/html/2609.11987v1)
studies paired comparisons and distinguishes completion from correctness; our
exposed adaptive panels cannot support its kind of contamination-controlled inference.
[pytest documentation](https://docs.pytest.org/en/stable/explanation/pythonpath.html)
already explains local/installed import selection. These works bound the novelty:
our contribution is the specific empirical source/process diagnosis and executable
evidence resource, not discovery of import resolution or harness verification.

[Google AI Edge Gallery](https://github.com/google-ai-edge/gallery) and
[AutoDroid-V2](https://arxiv.org/abs/2412.18116v3) establish prior offline mobile
interfaces and on-device workflows. Our intended use case is a repository workbench
that presents generated edits separately from source-qualified checks and verified
repairs. A native E2B harness supplies scoped file tools, hash-checked edits and
unchanged exports for host grading. It does not provide a phone Python/shell verifier.
## Reproducibility and limitations

The [current server resource12](https://www.kaggle.com/datasets/manimaran2308/requests-source-provenance-replay-v1)
contains60 byte-verified members and14 replay/fresh checks, including nine model
studies. It excludes the new process experiment, tenth model study and sensitivity
analysis, multi-library controls and physical-phone evidence in this local revision. Their frozen drivers, scalar inputs and outputs
are prepared for one reviewed final supplement before this revision is submitted.
The source guard and fresh drivers use Python3.11+, Git and local prerequisites;
missing prerequisites stop rather than download dependencies. Authored code uses
MIT licensing; research data/figures use CC BY4.0.

The natural Requests sample is small and exposed. Synthetic loops do not establish
model choice of the intervention. Constructed controls demonstrate mechanisms, not
real-world rates. A preflight probe does not instrument a later test, while the
original process control covers one synthetic module and the new API control covers
three source snapshots with fixed assertions. Namespace packages,
extensions, plugins, concurrent changes and unobserved workers remain outside the
measured scope. Source identity alone establishes neither issue relevance nor
regression safety. Reference patches can qualify fixtures without proving every
acceptable implementation is covered by their assertions.

Private-scoring equivalence,
improved leaderboard performance and prize quality remain unestablished. The resource
helps a local coding interface state what its workflow actually verified.
